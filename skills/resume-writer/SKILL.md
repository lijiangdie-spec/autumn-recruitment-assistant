# 秋招助手简历撰写协议

本技能随开源程序分发，技能目录中没有、也不得创建用户数据。个人资料、偏好、素材、岗位和
输出文件由秋招助手从系统级外置数据目录提供。代理只处理本次 prompt 中给出的资料、已确认
素材和 JD。

## 不可突破的边界

1. 公司、岗位、角色、技能、个人贡献、数字和成果必须能追溯到用户已确认素材；代码只能证明
   技术与实现，不能自动证明作者身份、个人贡献或业务结果。
2. 旧简历或仓库中缺失的信息留空并进入 `gaps`，不得反推、补造、夸大或“合理化”。
3. 未确认草稿、私人备注、素材来源路径、投递进度和登录信息不得进入简历。
4. JD 的要求不等于用户的能力。素材不支持的 JD 项只进入 `gaps`。
5. 不使用空洞能力宣言。用动作、方法、交付物和可核验证据展示能力。
6. 一页限制通过选材和删减实现，禁止缩字号、压行距或缩边距硬塞。
7. 不修改任何文件。秋招助手负责校验结构化输出、渲染、原子写入和版本管理。

## 三种素材入口

### 结构化访谈

说明“写进素材库不等于写进每份简历”，依次收集：背景与目标、用户角色与分工、方法与关键
决策、交付物和结果、难点、可核验数字、关键词。每轮最多问 2–3 个问题。所有答案先存草稿，
由用户确认后才能用于简历。

### 旧简历拆解

逐段提取项目和实习事实。保留原文中已经写好的事实句；个人联系方式、兴趣、自我评价和无法
归属到项目/实习的宣传性文字不进入素材。原文没有的字段留空。

### 代码仓库分析

只读 README、包清单、入口、核心模块和测试；跳过 `.env`、凭据、依赖目录、构建产物和用户
数据。可提取技术栈、架构、功能和测试证据；个人角色、动机、业务指标和性能数字必须由用户
另行确认。

## 按 JD 生成

1. 解析岗位职责、硬性要求、技能关键词和加分项。
2. 只从 `status=confirmed` 的素材中选取最相关事实。强相关经历给 2–3 条要点，弱相关经历压缩
   或舍弃。
3. 每条要点使用“简短导语 + 动作 + 方法/工具 + 可核验结果”。只有素材支持时才靠近 JD 术语。
4. 姓名、电话、邮箱、教育和技能只能来自个人资料对象。
5. `covered` 只列正文实际覆盖的 JD 项；`gaps` 列 JD 需要但素材没有的项。
6. `accentHex` 使用用户偏好，不自行猜测公司品牌色。
7. 首次 `revision=1`；改写在当前版本上加一。只输出调用方 JSON Schema 允许的对象。

## 渲染与 QA

秋招助手负责以下动作，代理只需控制内容密度：

- PDF：`assets/template_c.tex`，XeLaTeX 编译两遍，检查单页、文本提取、占位符、页尾位置和预览图。
- Word：`scripts/build_docx.mjs`，A 为经典单栏，B 为双栏。
- QA 失败时优先删除弱相关项目或次要要点，不得编造补位。

最终输出应让每句话都能回答：“这条事实来自哪一段已确认素材？”
